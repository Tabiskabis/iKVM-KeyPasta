## 1. The problem

Supermicro BMCs (made by ATEN) offer a remote console in two forms: a Java app (from IPMIView, or as a `.jnlp` file from the BMC's web interface) and an HTML5 viewer in the browser. Both handle the keyboard by *character*, not by *key*, and assume a US keyboard on both ends.

**Java app.** It doesn't forward key positions. Java turns each local key into a Java key code via the character the key produces on the *local* layout, and the viewer looks that code up in a fixed US table. With a Swiss keyboard, some positions (`^`, `¨`, `$`, `-`) can't be reached at all, AltGr arrives with an extra Ctrl, and Y and Z are swapped.

**HTML5 viewer.** It's an old noVNC. It turns the typed character into the US key position of that character (`ast2100.js`), sends only left-hand modifiers, never AltGr, and has nothing for the ISO key (`< >` left of Y on European keyboards).

**What the project wants instead:** the remote console behaves like a keyboard plugged into the server. Every key arrives at its physical position, and the *remote's* layout decides what it types. Then any local layout works with any remote layout, dead keys and AltGr included. On top of that: paste the local clipboard into the remote by typing it, and a few things only possible from outside the viewer (Ctrl+Alt+Del, Alt+Tab).

Two rules follow from the target users (most of them with Swiss keyboards, on BMCs that have been set up long ago):

- **Never require changing the iKVM "Keyboard layout" setting.** It stays English on countless BMCs, and it's stored on the BMC.
- **Never require changing the local input layout.** Typing must work with whatever layout the user has.

## 3. Keys

### Java viewer with the agent

A `KeyEventDispatcher` sees every key event before the viewer and gives each key of the main block the US key code of its *physical position*, so iKVM's US table turns it into exactly that position. The rest is left to the remote's layout.

Where the position comes from:

- **Windows:** the scan code in Java's key event (private field, low byte).
- **Linux:** the X keycode (minus 8).
- **macOS:** macOS has the key's position (its "kVK" code), but Java drops it. The agent patches Java's macOS key handling in memory while it loads (`MacKeys`): it keeps the code in the key event (in an otherwise unused field) and takes the position from there, whatever the local layout, dead keys and Option combinations included. If that patch doesn't apply (another Java version), a fallback: macOS gives every key except letters, digits and dead keys the US key code of its position anyway; for letters, digits and dead keys the agent derives the position from the known local layout (Swiss German, Swiss French, German or US), read from the current input source (`localLayout=` overrides it), and corrected from the characters of keys like ö, ' or ß when the input source said otherwise. macOS gives the key left of 1 and the ISO key the same key code: the agent tells them apart by their character (§ ° ± ¶ • ^ ¬ and US \` ~ are left of 1, anything else is the ISO key), so AltGr+< works.

Other key handling, all OS unless noted:

- **AltGr's extra Ctrl** (Windows sends AltGr as Ctrl+right Alt) is held back 20 ms and dropped if right Alt follows.
- **Left Ctrl is followed by an F24 release.** In iKVM's "stable keyboard" mode a held left Ctrl is dropped when the next key goes down, but a key release sends it. F24 is never pressed, so its release has no effect on Linux or Windows remotes.
- **CapsLock per window** (Windows): each viewer window keeps the remote's CapsLock state, other programs keep theirs.
- **Lock keys on macOS:** iKVM sends a Mac lock key as a tap at press and again at release (Mac CapsLock semantics), which toggled it back. The release is dropped, and lock keys aren't kept in the list of held keys (a focus loss toggled the remote's CapsLock).
- **The keypad's Clear key is NumLock on macOS** (it sits there; Macs have none, and the remote's NumLock decides whether the keypad types digits).
- **Command is the remote's Windows key** on macOS.
- **The viewer's LED sync types lock keys on Linux** (and in the container): when the BMC reports LEDs other than the local ones (or the viewer gets the focus), iKVM's Linux library sets the local lock state by typing the lock key (XTest). That key went to the viewer, which sent it to the remote: its CapsLock toggled back, so (depending on when the remote reports its LEDs, the Linux console late) only every second CapsLock seemed to arrive. The agent notes those calls (`Native.changeLEDstate`) and drops that lock key's press and release right after, as it does Windows' own sync key.
- **CapsLock as the viewer sends it:** not as press and release but as one code per toggle, by the local state: `0x39` (on) or `0xff39` (off). The BMC presses CapsLock on the remote when that differs from the remote's LED. The BMC sends no LED reports, so the remote's lock state can't be known; the viewer's virtual keyboard has its lock keys. Other ways that were tried: see [15](#15-tried-and-dropped).
- **Caps Lock: Simplified** (KeyPasta Preferences, instead of "With LED syncing"; Windows and Linux; macOS does it always): no LED reading or syncing at all, and CapsLock sent once per press with the local state from Java, as on a Mac. Without it, Windows' and Linux's libraries send it by the local LED and the viewer as a press and a release (a whole key at the release in its stable keyboard mode), and with the Windows viewer a Linux text console lost every second CapsLock. With it, the local CapsLock light no longer follows the remote's (on BMCs that report it) and isn't set again when switching windows (Windows).
- **Alt and Command swapped, if asked** (Options › KeyPasta Preferences: a default and the BMC's own, by the host in the viewer's title; or `swapAltCmd=true`): Command is the remote's Alt (the right one its AltGr), Option its Windows key, so a Mac keyboard has Alt next to the space bar, as on a PC. What Karabiner-Elements' rule did, without Karabiner, and in the container too. Elsewhere it swaps Alt and the Windows key, which is what Command is in the container's browser view. By the key's side: Linux Java gives the Windows keys and AltGr no side, the agent takes it from the X key code (133/134, 108). Shortcuts macOS or the browser keep for themselves (Cmd+Tab, Cmd+Q, Cmd+W in a browser tab) still don't reach the remote.
- **Focus loss releases what the remote has down,** with Alt and Win/Cmd broken up by a Ctrl tap first: otherwise Alt+Tab or Cmd+Tab away leaves the remote with a lone Alt or Win (menu bar, Start menu).
- **macOS reports no key release while Cmd is held:** such keys are released when Cmd goes up.
- **Keys for another part of the viewer window** (its toolbar, a button: the focus can stay there after a dialog, e.g. Record's) go to the remote too, and the viewer gets the focus back when such a dialog closes. Text fields, combo boxes and open menus keep their keys.
- **Media and browser keys** on Windows keep no position: their extended scan codes' low byte is a letter's (Volume Up E0 30 = B).
- **iKVM's own "Keyboard layout" setting is ignored for the keys** while the keyboard fixes are on: German would swap Y/Z and minus, French A/Q, W/Z, M; "Swiss" in that list has no effect at all. The viewer also switches the local input method to that setting's language (and its virtual keyboard to its own): on macOS that changed the Mac's keyboard layout, e.g. to ABC for English, so a Swiss keyboard typed QWERTY. Those switches are left out too.
- **Input methods are off for the viewer** (Windows, Linux: on Linux they swallowed dead keys). Not on macOS: there, turning them off made every mouse movement slow. Instead, a dead key's composition is ended right away, otherwise the next key's press doesn't reach Java.

Nothing else in iKVM is changed for the keys, so any viewer version works as long as its key class is `tw.com.aten.ikvm.ui.RemoteVideo`.

The Options menu gets a "KeyPasta Preferences" entry. **Every setting there has a default and, per host (the BMC in the viewer's title, "Current host: ..." at the top), a value of its own or the default's:** keyboard fixes, Alt/Command swap, Caps Lock (Windows, Linux), paste on or off, the paste hotkey (recorded: click its field, press the combination; Esc cancels. Without Ctrl, Alt or Meta only F1-F24, Pause, Scroll Lock or Print Screen, as any other key couldn't be used on the remote any more; one that isn't allowed beeps and recording goes on), remote layout, characters not on the keyboard, Alt codes for Linux or Windows. A switch shows one level at a time, "Current host" or "Default"; for the current host, values taken from the default are grey and italic ("default"), changed ones its own (blue, "own"). "Reset current host to default" (in the current host's view) drops its own values; "Hosts with own settings..." (in the defaults' view) lists every host that has any, with what they are, each to reset. The two buttons share one place, so nothing moves when switching.

The settings are kept in a plain text file, `agent.properties`, the same on every platform (copy or sync it between users and computers; where it is: the table in [2](#2-the-parts-and-how-they-work-together)). A default as `name=value`, a host's own as `name@host=value` (escaped as Java properties, so an IPv6 host works). Each save reads the file fresh and changes only what the dialog changed, written to a temporary file and renamed into place, so two viewers saving don't lose each other's settings. Until the viewer knows its host (its title), the default hotkey counts; on macOS `alt+shift+V` takes Cmd+Shift+V too.

### Java viewer with AutoHotkey only

Java builds its key table from the layout named in the last `WM_INPUTLANGCHANGE` message it received. The script sends the viewer such a message naming the US layout whenever an iKVM Java window becomes active (and again after a layout change). Windows stays on the local layout, only Java's table changes. The script then sends each physical key of the main block as the US key code of that position (the ISO key as F21, which iKVM maps there) and drops the extra Ctrl of AltGr. On suspend and exit, Java gets its real table back. If the US layout isn't loaded, it's loaded in the background (not activated, not shown in the language bar) and unloaded on exit.

Lock keys only work when iKVM sends them as one press+release message, which it only does for keys released within its "Repeat Key timeout" (default 200 ms; that's also why the timeout must not be 0). So the script sends every CapsLock press as one quick tap. NumLock and ScrollLock: press them briefly (the same trick for NumLock keeps it from reaching Java at all).

### HTML5 viewer

- **With the userscript:** it replaces the viewer's keyboard handling and sends the browser's physical key position (`event.code`) as USB key code, right Alt and the ISO key included. A key pressed with Cmd held on macOS is sent as one tap right away (macOS reports no release while Cmd is held; the key would otherwise stick on the remote and repeat).
- **AutoHotkey only:** the script sends, for each key, the character US has at that position, so the viewer maps it back to the right position. AltGr characters and the ISO key go as alt codes, as the viewer can't send them.

### What works where

See the table in the README. In short: everything works with the agent or the userscript; with AutoHotkey alone, the HTML5 viewer gets AltGr characters only as alt codes, and dead keys only without AltGr.

## 4. Paste

`Alt+Shift+V` types the clipboard into the remote (macOS: `Option+Shift+V` or `Cmd+Shift+V` in the Java viewer, `Cmd+Shift+V` in the browser; the agent and the userscript take another one, a default and per BMC, in their settings). The agent, the userscript and the AutoHotkey script paste the same way; the agent and the userscript from inside the viewer, sending the same key events as typed keys.

**The remote's layout can't be known, only said.** Each character is typed with the key that produces it on the remote's layout. Fast paste knows four layouts: Swiss German, Swiss French, German and United States (the agent's and the userscript's tables are identical and checked against X11's `ch`, `ch(fr)`, `de`, `us`). Default (agent and AutoHotkey script): the first of Swiss German, Swiss French, German and United States among your local keyboard layouts, in that order, else Swiss German. US comes last, as a Mac has ABC (US) next to its own layout. Local layouts: macOS's enabled input sources; Windows' input language list, each language's keyboard layout (English with a Swiss German keyboard counts as Swiss German; a layout of your own as none of the four); Linux's X layouts (`setxkbmap -query`). Not the system language, which often isn't the keyboard's. The userscript can't see the local layouts: Swiss German. Where it's set:

- AutoHotkey: tray menu "Remote layout": for the BMC of the last active Java viewer, else the default; kept in the registry (`HKCU\Software\iKVM-KeyPasta`), apart from the agent's.
- Agent: Options › KeyPasta Preferences: a default (the local one above unless set, or the `remoteLayout=` option) and optionally the BMC's own (by the host in the viewer's title), kept in `agent.properties`.
- Userscript: its settings dialog: a default and this BMC's own (by host), kept in the extension's storage.

If a character is on several keys, the one with the fewest modifiers wins. Dead-key characters and everything not on the keyboard are sent as **alt codes** (Alt + numpad digits):

- Windows reads `Alt+nnn` as OEM code page and `Alt+0nnn` as ANSI; the Linux console reads both as Unicode. So 160–255 always get the leading 0 and work on both; only the Windows-1252 characters 128–159 (€, curly quotes, dashes) differ, hence the "Remote OS" setting.
- ¦ always goes as an alt code: it's AltGr+1 on Windows' Swiss layouts but `|` on Linux.
- Line breaks are sent as one Enter each.
- Alt codes only type characters (no shortcuts, no dead keys), only on Windows and the Linux console, and on Windows only with NumLock on.

**Safe paste** (CapsLock on while pasting, or the layout set to "other"): everything as alt codes except line breaks, Tab and Space (the same on every layout). Slower, but works with any remote layout.

**Questions before pasting.** If the text has line breaks or AltGr characters (harmful if the remote uses another layout) or characters that aren't on the keyboard, a short dialog asks: fast paste, safe paste or cancel. Once the layout is set, line breaks and AltGr characters aren't asked about any more; what to do with characters not on the keyboard can be set too (ask, alt codes, leave out).

**Stopping.** Switching to another window or pressing Esc stops a running paste. Keys pressed during a paste (agent) are swallowed together with their release, so the remote doesn't get half a key.

**Speed.** The Java app paces the keys itself (`keyDelay=` for the agent; `JavaKeyDelay`, `JavaKeyPressDuration` in the AutoHotkey script). The HTML5 viewer takes keys much faster than the BMC types them: the rest piles up in the BMC, freezes the viewer and keeps typing after Esc and even a page reload. So pasting there waits 10 ms per keystroke (`HtmlKeyDelay`, userscript `KEY_DELAY`).

**The hotkey** is matched by letter, like Ctrl+V, wherever V is on the local layout (`paste=` for the agent, `PasteHotkey` in the AutoHotkey script, the userscript's settings dialog; the userscript takes a letter, a digit or F1-F24 as its key, not the agent's other key names). On macOS, Option+Shift+V types no character on the Swiss layouts, and Java dropped such key events entirely; the agent's key patch gives them their unmodified character so they arrive. Cmd+Shift+V is matched by the physical V key, as macOS reported it as C with Cmd held.

**In the container's browser view** the hotkey pastes the Mac's clipboard, without noVNC's clipboard panel: a small script in the page (`mac/container/keypasta.js`) takes the hotkey before noVNC does, reads the browser's clipboard, hands it to the container's clipboard (noVNC's clipboard, TigerVNC's extended clipboard: UTF-8; an older noVNC, 1.0.0, had Latin-1 only; the image has Ubuntu 26.04's 1.6.0), then sends the hotkey's key on, where the agent pastes as anywhere. Chrome and Edge ask once per port whether the page may read the clipboard; not allowed: the container's clipboard is pasted. The page asks for the hotkeys at `keypasta.json` next to it, which the container's web server (`keypasta-websockify`) answers from `agent.properties` at each request: every hotkey there, the default and the hosts' own, as the page can't know which BMC's viewer has the focus. The hotkey's key counts by its place on a US keyboard on macOS (the physical key, main block; other keys by their code) and in the container (its X layout is US); the dialog records it the same way. The browser view knows letters, digits, F-keys and the common named keys (navigation, numpad, punctuation); a hotkey with another key still pastes there, the container's clipboard instead of the Mac's.

**The userscript** needs the BMC opened with `https://` (browsers give the clipboard to secure pages only), and the browser may ask for permission (Firefox shows a small "Paste" button each time).

## 5. The Java agent: loading, safety, options, log

**Loading.** Java loads the agent for every Java program started with `JAVA_TOOL_OPTIONS=-javaagent:<path to the jar>`. The agent does nothing in programs that aren't IPMIView or the iKVM viewer: it installs its keyboard part only when the viewer's class `tw.com.aten.ikvm.ui.RemoteVideo` loads, and its IPMIView part only when IPMIView's main class loads. Its changes to IPMIView's and the viewer's code are made in memory while the classes load (bytecode, mostly redirecting a call to the agent's own method), never on disk: IPMIView's and the viewer's files stay unchanged, and an update of either just means the agent's change doesn't apply (logged) where the code changed.

**Safety.**

- `premain` never throws: an exception there would stop the JVM, i.e. IPMIView. The key dispatcher passes a key on unchanged if it fails.
- **On the bootstrap class path** (`Boot-Class-Path` in the jar's manifest): Java Web Start (.jnlp) runs the viewer under a security manager that gives class path code no permissions. Loaded by the bootstrap loader, the agent has them.
- **A missing jar stops every Java program.** If `JAVA_TOOL_OPTIONS` points to a jar that isn't there, *any* Java program silently doesn't start. The Windows launchers set the variable only for their own start, and skip it if the jar is missing; `uninstall.cmd` refuses to remove the jar while the variable points to it.
- **Install location:** the viewer runs as admin on Windows (and loads the jar), so the jar belongs in a folder only admins can write to (`%ProgramFiles%\iKVM-KeyPasta\`). A user-writable copy would be a way to admin rights. On Linux and macOS the viewer runs as the user, so a copy in the user's home gives nothing away; a system-wide copy belongs to root, so that no user changes what the others run. The Windows launchers take the jar from their own folder, else one folder up (started from the repo: `windows\` and the built jar above it), never from elsewhere (no variable, no argument): both places are as safe as the launcher itself, as whoever may write the folder above may also replace the launcher's own; any other place would let a program running as you choose what runs as admin.
- **The log never shows typed keys or passwords:** only decisions, the first use of each modifier, program names (not their arguments: the Windows viewer's command line has the user name and password).

**Options:** `-javaagent:...jar=name=value,name=value`:

| Option | Default | |
|---|---|---|
| `paste=` | `alt+shift+V` | the default paste hotkey: modifiers (ctrl, alt, shift, meta/cmd) and a key: a letter, a digit or a Java key name (`F12`, `INSERT`, `NUMPAD5`, `SEMICOLON`). The dialog's setting wins. |
| `pasteNonAscii=` | `ask` | characters not on the keyboard: `ask`, `always` (alt codes), `never` (left out) |
| `remoteOs=` | `linux` | `linux` (console) or `windows`: alt codes of the Windows-1252 characters 128–159 |
| `remoteLayout=` | `auto` | the default remote layout: `us`, `de-CH`, `fr-CH`, `de-DE`, `other` (alt codes); auto: the first of Swiss German, Swiss French, German, US among the local layouts, else Swiss German (see [4](#4-paste)). The dialog's setting wins. |
| `localLayout=` | `auto` | macOS only, the fallback for key positions: `de-CH`, `fr-CH`, `de-DE`, `us`; auto: the current input source |
| `keyDelay=` | `2` | ms between keys when pasting |
| `loginTrace=` | `false` | `true`: IPMIView's threads in the log for 20 s after a BMC's view opens (why a login is slow) |
| `swapAltCmd=` | `false` | Alt and Command (elsewhere: the Windows key) swapped, see [3](#3-keys). The dialog's setting wins. |
| `mouseRate=` | `60` | mouse moves sent to the BMC per second at most, `0`: every one (see [6](#6-the-java-agent-fixes-in-the-ikvm-viewer)) |
| `log=` | (none) | debug log file |

Unknown options and values are ignored with a message on the console. The settings in the viewer's Options › KeyPasta Preferences (`agent.properties`, see [3](#3-keys)) win over the options.

**Building:** `java-agent/build.sh` or `build.cmd` (a JDK 9 or newer; the jar runs on Java 8 and newer). `build.cmd` takes `javac` from `PATH`, else from `JAVA_HOME`, an installed JDK (Eclipse Adoptium, Microsoft, Zulu, Oracle, OpenJDK) or IPMIView's own Java, which is a full JDK 11; on Windows `javac` is rarely on `PATH`. `java-agent/stub/` holds compile-only stand-ins for macOS's and IPMIView's classes, not part of the jar; `java-agent/hook/` the class the agent defines in IPMIView's class loader (in the jar as `keypasta/KeyPastaStunnel.bin`, data, not a class: the agent's own classes are on the boot class path, where it would be loaded wrongly).

## 6. The Java agent: fixes in the iKVM viewer

**Window size.**

- **New remote resolution, window in the background:** the `.jnlp` viewer resizes its window to a new resolution only when the window is activated (and shrank it to 320×240 meanwhile). The agent does it right away.
- **Auto-resize on, window bigger than the video:** packed again (seen under WSLg: wide empty margins right and below).
- **Window left at 320×240:** on connecting and on a new resolution the viewer sets its window to 320×240, then fits it to the picture. In the Mac app's container that second step didn't take, and the window stayed tiny with scroll bars. Still that size a second later with the picture running: fitted to the picture (at most the desktop). A size set by hand is left alone.
- **Wayland and WSL (WSLg): windows stay resizable.** A fixed-size window there kept a wrong size (empty margins right and below the video), and Java lost track of its position (menus and clicks offset, the window jumping back on every resize). Reproduced with Weston's X window manager, the same as WSLg's. The viewer's `setResizable(false)` calls are turned into `true`; a property listener restoring it afterwards was too late.
- **The viewer no longer forces itself on top** (`setAlwaysOnTop(true)` becomes `false`).

**Preferences window:** 140 pixels wider and resizable (it cut its content, worst with the Mac font), every OS.

**Mouse moves** are sent to the BMC at most 60 times a second (`mouseRate=`), always the latest position; buttons and the wheel go at once. *Why:* the viewer sent every mouse move Java reported as its own packet, with a fast mouse or trackpad hundreds a second (Windows passes on nearly every hardware report; macOS merges them to the display rate, so Windows was worst). The BMC can't keep up: the frame rate dropped while the mouse moved, more the longer it moved, and needed a while without movement to recover. Single mouse mode sends movements rather than positions and is left unchanged.

**macOS: the virtual keyboard window** is 8 pixels higher (its bottom row was cut by today's taller title bar).

**macOS: the menus in the Mac menu bar.** The agent turns on Java's screen menu bar (`apple.laf.useScreenMenuBar`) for IPMIView and the viewers, adds its KeyPasta item to the viewer's Options menu (the Mac menu bar mirrors a menu's items and never shows its Swing popup, so the item is placed right away and again whenever the viewer adds one), and removes the viewer's Exit menu (Quit and the close button do that). **Cmd+Q goes to the remote** (as Win+Q, or Alt+Q with Alt and Command swapped) instead of quitting the viewer: macOS's menus take a shortcut before the window gets the key, so the agent has Quit's Cmd+Q shortcut removed (native code in `java-launcher`, like the menu bar watch below); the Quit item still quits when clicked, and so does the window's close button.

**macOS: focus and menus after dialogs.** After the launch, after Preferences closed, and above all after Record's two dialogs (save file, video size), the viewer's app was in front but none of its windows had the focus: keys went nowhere, and the Mac menu bar showed only the app menu or was grey, until the mouse moved over the viewer or another app was activated and the viewer again. What happens (from the JDK 11 sources): when a window becomes key, Java installs its menus, greyed if the window is disabled at that moment. After Record's dialogs macOS made the viewer key while Java still had it blocked by the closing dialog: Java dropped that activation, the menus came in grey, and since macOS had the window as key already, no further activation came. What the agent does, when the app is in front, no window is focused and no other window of it is showing:

1. It asks for the focus (enough after the launch and after Preferences).
2. A second later, if still unfocused and macOS has the viewer as its key window, it hands Java the activation it dropped (the call macOS's "became key" notification makes).
3. Once the viewer has the focus after that, it rebuilds the viewer's menu bar (taken away and given back), so the menus come back enabled.

**macOS: the menu bar redrawn when its menus change.** **macOS 27 doesn't redraw the menu bar when an app changes the menus in it**: they show only once the pointer goes to the menu bar or the app is switched. (Also seen by the FlatLaf project, with plain Swing too; their remedy is the same.) Setting the app's main menu to nothing and back makes macOS redraw it. The agent used to guess when that was needed (after the focus came back, after IPMIView's start) and still missed cases. Now macOS says it: native code watches the menu bar itself, through AppKit's own notifications (a menu added to, removed from or changed in the bar, the app coming to the front, a window becoming key or main), and 50 ms later (a burst of changes: one check) redraws the bar if what it shows changed (the menus' names, which are grey) or the app came to the front. A change inside a menu needs no redraw, and the redraw's own notifications don't count, so it can't loop. What the bar shows is logged whenever it changes: whether the app is in front, the key and main window (their kind and number, not their titles), the menus in the bar and which are grey. That tells "menus never set", "set but not drawn" and "set but grey" apart. It runs in IPMIView and in the viewers. The native code is in the Mac app's `java-launcher` (the program the app runs IPMIView and the viewers in, see [13](#13-macos-the-app-the-scripts-the-container)), as a JNI library built into that program, so there's no extra file. Without the Mac app, nothing is watched (logged). Tested on macOS 27 (2026-10-28): the menus no longer go missing.

**IPMIView too:** its menus were missing from the menu bar after it started (the app menu only). The menu bar watch covers it, and IPMIView's main window gets steps 1 to 3 above while its app is in front with none of its windows focused.

**macOS: keyboard LEDs.** iKVM's macOS library reads and sets the keyboard LEDs (CapsLock) by opening the keyboard as a HID device, and *quits the viewer* (`exit(1)`, no crash report) when macOS refuses that, which it does without the Input Monitoring permission. It does that on every focus change (any dialog), on the BMC's LED reports and for lock keys. The agent leaves out all of those LED calls and gives lock keys their state from Java instead, so no permission is needed.

**macOS: the viewer's stunnel.** A `.jnlp` viewer unpacks its own `stunnel` (the encrypted tunnel to the BMC) into a new temp folder on every start: for the macOS firewall (e.g. LuLu) a new program every time. The agent runs Homebrew's stunnel instead, same arguments, or else a fixed copy of the viewer's own in `~/Library/Application Support/iKVM-KeyPasta/stunnel/` (rewritten only when the viewer brings a different one). The viewer stops its stunnel with `killall` by name when it closes; the agent stops the redirected one itself.

**Icons.** The viewer has no icon of its own (Java's): it gets KeyPasta's on its windows, and on macOS in the Dock, dark or light with the system appearance (followed while running). IPMIView keeps its own window icon; on macOS its Dock icon (Java's otherwise) is set from it.

## 7. The Java agent: fixes in IPMIView

IPMIView is Supermicro's management program; it lists BMCs, logs in to them and starts the Java viewer. IPMIView's About dialog gets a "KeyPasta agent" tab with the project page; it lists these changes as they apply on the running OS.

**Faster console launch.**

- After starting its tunnel (stunnel), IPMIView waited a fixed 4 seconds. Now only until the tunnel is ready, usually a fraction of a second (checked by the tunnel's port being taken).
- Then it checked the port itself, bound on all addresses, which macOS allows next to stunnel's on 127.0.0.1: "not in use", so it started stunnel again every half second until 4 more seconds were up (ten extra stunnels per console). That check goes to the agent's too (on stunnel's own address): one stunnel, the viewer about 4.5 s sooner.
- On Linux and macOS the viewer paused 5 seconds after reading its settings from IPMIView, before connecting. That pause is skipped.
- With `log=`, every launch step is logged with its time (BMC questions, tunnel, test login, viewer start, connecting, logged in, viewer window, first picture).

**The encrypted console on macOS.** IPMIView has the Mac code for its tunnel (`MACStunnel`: stunnel and its configuration from `BMCSecurity/mac/`, which `ipmiview-keypasta.sh` provides), but one method refuses on macOS: `StunnelFacotry.createStunnel`, "The function can't support on mac". The agent sends IPMIView's call of it to a small class of its own, which asks IPMIView's method first and only replaces that refusal with a `MACStunnel`. So a later IPMIView keeps whatever its own method does (Mac support of its own included), and one without a usable `MACStunnel` gives its own answer, with the reason in the agent's log. That class has to live in IPMIView's class loader (it returns IPMIView's own type, which the agent's classes can't name): the agent defines it there when IPMIView's tunnel code loads, from a file in its jar (`java-agent/hook/`, compiled against stand-ins in `java-agent/stub/`).

**No settings file with the password.** On Linux and macOS, IPMIView handed the viewer its settings (user name, password, ports) in a file `<BMC>.temp` in the temp folder, readable by other users. When the viewer runs with the agent too (which the Mac app and a global `JAVA_TOOL_OPTIONS` ensure), IPMIView hands them over through the viewer's standard input instead, and the file is never written. Otherwise the file as before.

**No needless questions.**

- IPMIView quits without asking "Are you sure to quit?" (other questions, like saving a changed configuration, stay).
- Closing a BMC's session no longer shows the note about closing its KVM console.

**Main window:** 20 pixels wider on Windows, 60 on Linux, 1144 pixels wide on macOS (for the wider Mac font). On macOS also its status line gets some margin (the rounded window corners cut the text).

**Fonts.** IPMIView sets its own font, PMingLiU (a Taiwanese font with thin, hard-to-read Latin letters), on macOS and Linux.

- **macOS:** SF Pro if installed, else Helvetica Neue, 13 pt. Only fonts macOS lists to Java are drawn with macOS's own text rendering; the system copy of San Francisco isn't listed, and loaded from its file Java draws it visibly heavier.
- **Linux:** Noto Sans, DejaVu Sans or Liberation Sans (the first installed), 12 pt, and antialiased: Java takes antialiasing from the desktop's settings, and without a desktop (e.g. WSL) it was off, showing PMingLiU's jagged built-in bitmaps.
- **Text cut by the wider font** (IPMIView's fixed label widths were made for PMingLiU): labels and buttons are widened where there's room, else made smaller or given a tooltip; dialogs grow towards their preferred size. **Windows laid out by coordinates** (the Flash Tool) are made big enough for their content (under WSL their frame took a part of them).
- **macOS: no boxes in boxes.** Aqua's tab panes draw a rounded box around their content; inside IPMIView's own boxed panels that gave boxes in boxes. The agent turns that box off for IPMIView's tab panes.

**Login.** IPMIView's "Save ID and Password" keeps the password in `account.properties`, obfuscated (AES with the device name as key; IPMIView decrypts it itself to fill the login view).

- The password field of the login view gets an **eye button** that shows the password.
- **A renamed device keeps its saved login.** IPMIView leaves the saved ID and password under the old name when you rename a device (Edit device), and its login view looks them up by name only, so the login came up empty while the firmware update popup (which also tries the IP) still found them. The agent moves them to the new name (and to a new IP if that changed). A device renamed before this fix gets the login saved for its IP copied to its name when its login view opens.
- **IPMIView's window without Supermicro's brand** (`Unbrand`): its title without " - Super Micro Computer, Inc." (taken off again if IPMIView sets it again), and without the Supermicro logo at the top left (a link to supermicro.com): its panel is removed, the BMC list moves up (IPMIView's files stay unchanged).
- The firmware update's login popup ("Please input ID and Password") is **filled with the BMC's saved ID and password** (it asked again although they were saved).
- **Removing a system** from IPMIView's list also removes its saved ID and password (by name, and by IP address if no other system has it).

**All settings in the settings folder.** IPMIView can be given a settings folder (its second argument; the Windows launcher with `%APPDATA%\IPMIView`, the Linux and macOS starters always). It keeps the BMC list and logins there, but opens some settings files by their bare name in the folder it runs in, its program folder: `sort.properties` (read there, written to the settings folder: "Do not show this dialog next time" never stuck), `language.properties` (read before IPMIView looks at its arguments: the language chosen never stuck), `smcrakp.properties` (written on every start), `update.properties`, `version.properties` (in a folder named `.\` on Linux and macOS). The agent opens these in the settings folder too (the one IPMIView was given, before that the `KEYPASTA_IPMIVIEW_SETTINGS` the starters set), so IPMIView's folder isn't written to. Without a settings folder nothing changes. Program configuration like `stunnel.properties` stays in IPMIView's folder.

**The settings folder in its notes.** After File › Save, IPMIView says where it saved `IPMIView.properties` ("The configuration file has been save to"), Help › Configuration tip says the same folder. It made the folder's path with `new File(".").getAbsolutePath().replaceAll("\\.", "")`, meant to take off the trailing `.`, but taking out every dot: `~/.config/ipmiview` showed as `~/config/ipmiview`, `IPMIView_2.25.0` as `IPMIView_2250`. The agent sends that call to its own, which takes off only the trailing dot, and the note says "has been saved to".

**Sensors.** A BMC's Sensors tab opens in its **text view** (the graphic view was the default), which gets a **"Clear Chassis Intrusion"** button next to Refresh (only the graphic view had one). It asks IPMIView's own question, sends the same Supermicro command as the graphic view's "Clear" (`ipmitool raw 0x30 0x03`), then reads the sensors again.

**Faster first login.** IPMIView looked up the computer's own address (`InetAddress.getLocalHost`) for every connection to a BMC and every packet it sent. That resolves the computer's own name, which returns all addresses of all its network adapters; Java keeps the answer only 5 seconds and holds a lock while it asks. IPMIView checks the status of all listed BMCs every 20 seconds, one connection each, and the login queued up behind those lookups: on Windows with many adapters or VPN addresses, the first login after the start took long, longer the more addresses the computer has. In the classes changed, the address was only used where any address of the computer does (as the placeholder address of a packet to receive, and to wake IPMIView's own receiving connection), so they get the loopback address 127.0.0.1 without a lookup. Where the BMC is told the address (the old serial console redirection), or where the adapter matters (a MAC address used as a key), the lookup stays.

**macOS without Homebrew's stunnel:** IPMIView starts anyway, and a red note below "Launch KVM Console" says that the encrypted console needs it.

**Login diagnosis:** with `log=` and `loginTrace=true`, opening a BMC's session view or pressing a button in it logs 20 seconds of what IPMIView's threads do (where they wait), to find delays. Off by default: it filled the log with stack traces.

## 8. The HTML5 userscript

`iKVM-KeyPasta.user.js` runs in the BMC's HTML5 viewer page (Tampermonkey or Violentmonkey).

Kept in the extension's storage, not in the BMC's site data. The script's dialogs live in their own shadow root with their own styles (light and dark), so the BMC page's CSS doesn't reach them.
- **The viewer's own hotkeys** (Options › Hotkey Settings, e.g. Ctrl+Shift+F5 for Ctrl+Alt+Del) work again: the script's key handling had starved them; it now asks them first, and a key that matches one isn't sent.

The script keeps that warning for when it's asked for: a grayed out "Video recording (unavailable)" item (older viewer: in the Capture menu; newer viewer with a row of buttons, under `/redfish/…IKVM`: the record button, grayed out) shows it when clicked.

## 10. The AutoHotkey script

`windows/iKVM-KeyPasta.ahk` (AutoHotkey v2, Windows). Where the agent or the userscript is active (title marker), it only adds what they can't do; elsewhere it fixes the viewers itself (see [3](#3-keys) and [4](#4-paste)).

- **Ctrl+Alt+End sends Ctrl+Alt+Del to the remote**, as in Remote Desktop (the real one always goes to the local Windows). It asks first, Cancel being the default, since on a Linux console Ctrl+Alt+Del reboots the server right away; "Don't ask again for 4 hours" turns the question off for a while, `ConfirmCtrlAltDel := false` for good. Windows would make a local Ctrl+Alt+Del of a Delete sent while Ctrl and Alt are held, so Ctrl and Alt are sent and the Delete is posted to the viewer window as a message.
- **Alt+Tab in the Java app goes to the remote.** Windows opens its task switcher for every Alt+Tab, even a sent one, before Java sees it, so the Tab is blocked and posted to the Java window as a message. Locally, use Win+Tab or the mouse. (The HTML5 viewer can't get it.)
- **Paste in other programs:** `Alt+Shift+V` pastes plain text anywhere (tray menu to turn it off).
- **Tray menu:** remote layout (per BMC), remote OS (alt codes of €, curly quotes, dashes), non-ASCII characters (ask, include, omit), paste in any window or iKVM only, suspend. Every choice is saved in the registry, `HKCU\Software\iKVM-KeyPasta` (a BMC's layout in its subkey `RemoteLayouts`), and wins over the defaults at the top of the script. The script is Windows only and independent of the agent and the userscript, so it shares no settings with them. Elevated by a different admin account (a standard user's UAC prompt), it uses that account's registry.
- **Rights.** Windows refuses keystrokes and messages to programs running as admin (the iKVM Java app may) unless the script has UI Access or runs as admin itself. When that happens, it restarts itself with UI Access (`AutoHotkey*_UIA.exe`, part of the AutoHotkey installation), or else as admin (UAC prompt); declined: a notification, and the tray menu's first entry tries again. UI Access is only granted to programs in a protected folder (`%ProgramFiles%`): in a folder you can write to, any program running as you could change the script and get its rights. A compiled exe also needs to be signed (the README shows how with a self-signed certificate).
- **One instance:** starting the script again closes the running one, .ahk or compiled exe, from any folder and with any rights (the new one first restarts itself with the same rights, as Windows doesn't let a normal process close a privileged one).
- **`DebugMode := true`** records key history, executed lines and the messages to the Java app (tray menu). Never leave it on: the key history contains passwords.

## 11. Windows: installer and launchers

**`windows/install.cmd`** first runs `java-agent\build.cmd` (as the user) whenever the project's source is there (a git clone has no built files), every time, so an update never installs an old jar. If that fails, it warns and installs the jar that's already there; with none at all it stops. With the source there, the jar comes from the project's top folder, where the build puts it. Then (as admin) it copies whatever of the jar, the jnlp launcher, the IPMIView launcher, the .ahk or a compiled exe and the icons is there to `%ProgramFiles%\iKVM-KeyPasta\` (closing an installed exe first, as a running exe can't be overwritten), then as the user: registers the jnlp launcher, creates the Start menu shortcut "IPMIView with KeyPasta" (if IPMIView is installed) and a Startup shortcut for the script, and starts it. Without AutoHotkey v2 it offers to install it with winget (machine-wide: UI Access needs `%ProgramFiles%`); without OpenWebStart it offers that too. `windows/uninstall.cmd` undoes it; it refuses while `JAVA_TOOL_OPTIONS` points to the jar (see [5](#5-the-java-agent-loading-safety-options-log)). The copied `.jnlp` files in `%TEMP%` stay.

**`windows/iKVM-IPMIView-launcher.cmd`** (the Start menu shortcut): restarts itself as admin (not with `/noadmin`: IPMIView as the user then, and a viewer that asks for admin rights itself starts without the agent), sets `JAVA_TOOL_OPTIONS` for this start only and starts IPMIView. *Why:* the viewer runs as admin, and a process elevated by UAC gets its environment from the registry, not from the program that started it, so a variable set just for one start must be set inside the elevated process.

**IPMIView's settings in a folder of your own (if `%APPDATA%\IPMIView` exists):** `IPMIView20.exe` always runs in its own folder (`IPMIView20.lax`: `lax.user.dir=.`, relative to the launcher; editable, but only by admins, likely replaced by an update, and with no per-user path), and IPMIView reads and writes its settings files there by bare name, so a normal user can't save them (an error, no elevation). IPMIView takes a settings folder as its second argument (`IPMIView20.exe - "<folder>/"`: the first must be none of its flags, `d` debug log, `e` exceptions shown, `q` short timeouts, `forceUpdate`, and the OEM brandings `p s t x i c`; the folder is put right before the file names). The launcher does that when `%APPDATA%\IPMIView` exists: you create it and move or copy your settings files there yourself (nothing is copied for you; an empty folder: an empty BMC list); without it, IPMIView keeps them in its program folder. It's always your `%APPDATA%`, also when the UAC prompt asked for another account's password (a standard user): the launcher finds the folder before it asks and hands it to its elevated self, and an elevated admin may read and write your profile (not necessarily an AppData redirected to a network share, whose own rights count). It covers all of IPMIView's settings files: `IPMIView.properties`, `account.properties`, proxy and language, and the ones IPMIView itself still opens in its program folder (sort order, language at the start, ...), which the agent sends there too (section 7, "All settings in the settings folder").

**`windows/iKVM-jnlp-launcher.cmd`** (meant as the program for all `.jnlp` files; `/register` adds it to "Open with", where it's made the default by hand, as Windows doesn't let programs set defaults): an iKVM `.jnlp` gets the same treatment (elevation, `JAVA_TOOL_OPTIONS` for this start only), is copied to `%TEMP%\iKVM-KeyPasta\` under a name with date, time and BMC, and the copy is started with OpenWebStart, by a hidden PowerShell that then waits for the agent's file (the viewer, in a JVM of OpenWebStart's own, inherits the variable); the cmd window closes meanwhile. The original is removed only once a viewer window has opened from the copy, and only if it's still the same file (a newer download under that name stays): the launcher sets `KEYPASTA_VIEWER_OPENED` to a file name next to the copy (`launch-....opened`), and the agent (3.3.0 and newer, `ViewerStart.opened`) creates that file when the viewer's window shows, which the viewer builds only after connecting and logging in. Waited for up to 300 seconds (`VIEWERWAIT`; they include answering OpenWebStart's or IcedTea-Web's questions and a first Java download). Any other outcome (no window, as with "connect failed", or no agent) leaves the original where it was for another try. Compared by a hash taken before the copy's Java version is changed. Copies there are kept for a week after they were last opened, then deleted at the next start (Windows doesn't empty `%TEMP%` by itself, only Storage Sense if it's on, or Disk Cleanup). Any other `.jnlp` goes to OpenWebStart unchanged. Started without a file, it takes the newest `launch*.jnlp` in Downloads (browsers save the next one as `launch (1).jnlp` and so on). Settings at its top: `JNLP`, `OWS` (OpenWebStart folder), `JAVAVERSION` (default `1.8*`), `VIEWERWAIT` (default 300 seconds).

**Why the jnlp launcher elevates first.** The viewer asks for admin rights itself when it needs them (newer BMCs: USB media forwarding), right after it connects. Seen in a process log: its Windows library writes a `restart.jnlp` and has Windows start `javaws.exe restart.jnlp` elevated (found through PATH, hence OpenWebStart's folder in PATH), and the unelevated viewer ends. Windows gives the elevated process a fresh environment, so `JAVA_TOOL_OPTIONS` is gone and the viewer runs without the agent. Started as admin from the beginning, the viewer never restarts, and the agent stays. Ways around it, checked in OpenWebStart's code (`OwsJvmLauncher`, `JvmUtils`):

- `javaws` has no option that passes arguments to the JVM (no `-J…`).
- JVM arguments in a `.jnlp` are checked against a list of allowed ones; `-javaagent` isn't on it (`deployment.jvm.arguments.whitelist` can add one, compared by the whole argument up to its first `=`).
- `JAVAWS_VM_ARGS` (environment) is lost through UAC like `JAVA_TOOL_OPTIONS`.
- `ows.jvmargs.for.<file name>` in `deployment.properties` adds arguments for a `.jnlp` by its file name (the last part of its `href`, if it has one), unchecked, with double quotes for spaces. `ows.jvmargs.for.restart.jnlp="-javaagent:C:\\…\\iKVM-KeyPasta-agent.jar"` works: tested, the elevated viewer had the agent. Not used: the launcher would have to change the user's OpenWebStart settings, and every program that restarts through a file of that name would get the agent (and fail to start if the jar went missing). A machine-wide, locked entry (written by `install.cmd`) avoids the first but not the second.
- The agent doing the elevated restart itself (it runs in the unelevated viewer): only possible if the restart came from the viewer's Java code; the library starts it itself (`ShellExecuteExW`), out of the agent's reach, and the Java call leading there differs between viewer versions.

**Web Start and security.** The viewer's jars come from the BMC at every start (OpenWebStart caches them and checks for updates), and the ones seen so far are unsigned: nothing checks the code but the HTTPS connection to the BMC, whose self-signed certificate OpenWebStart asks about once and then remembers. The certificate among the `.jnlp`'s arguments is the BMC's console certificate: the viewer writes it into its stunnel folder as `server.crt` and has stunnel check the console connection against exactly that one (`CAfile`, `verify = 3`; seen in IPMIView's code). It pins the console connection, not the download, and it comes in the same download as everything else. It looks built into the firmware (a ten-year "IPMI" CA certificate from Super Micro Computer), so its key is likely in every copy of that firmware. Plain Web Start has all of this too; KeyPasta adds nothing to it (the viewer asks for admin rights on its own anyway). The container (`keypasta-jnlp-jars`) downloads the jars without checking the BMC's certificate at all (left so, the maintainer's choice).

**OpenWebStart with Java 8:** Java 11 and newer have no `javaws` for `.jnlp` files any more, OpenWebStart provides one. It must run the viewer with Java 8: the `.jnlp` files ask for Java options that Java 17 and newer refuse ("Unrecognized VM option 'PermSize=32M'"). Current Java 8 refuses TLS 1.0 and 1.1, which old BMCs may need (`jdk.tls.disabledAlgorithms` in that Java's `java.security`). The launcher sets the Java version in its copy of the `.jnlp` (`<j2se version="1.6.0+">` becomes `1.8*`), so that no OpenWebStart setting (`ows.jvm.manager.versionRange`) forces Java 8 on other programs; the viewer's own `restart.jnlp` gets Java 8 again by itself. The Javas OpenWebStart has downloaded are listed in its settings (`itw-settings.exe` › JVM Manager).

## 12. Linux: the desktop launcher

`linux/install.sh` puts IPMIView and iKVM Viewer (for `.jnlp` files) into the desktop's app menu (GNOME, KDE and others following the freedesktop.org standards), and the command `ipmiview`, all with the agent.

- **Which IPMIView:** the menu entry and `ipmiview` start the newest `IPMIView*` folder (by the version in its name, from its first digit on, `sort -V`; of equal versions the one in the place listed first) in `~/.local/share`, `~/.local/lib`, `~/.local/bin`, `~/Applications/IPMIView`, `~/Applications`, `/opt/SUPERMICRO`, `/opt`, `/usr/local/share` or `/usr/share`, so a new version needs no new install: unpacking its download into `~/.local/share` is enough. The installer takes the folder or downloaded `.tar.gz` given as argument; else the newest of those already there and of the `IPMIView*_Linux_x64.tar.gz` downloads in the current folder or the Downloads folder (`xdg-user-dir DOWNLOAD` and `~/Downloads`); else it stops and says where to download it (IPMIView 2.25 or newer is needed for current firmware) and how to run it with the download. A download is unpacked into `~/.local/share` (`--system`: `/opt`), a folder given that isn't in one of the places (or, `--system`, in a system one) is copied there; its name must start with `IPMIView`. If that isn't the newest one there is, it says which one will start. The settings (BMC list, saved logins) are not in it but in `~/.config/ipmiview` (below), so a new version finds them there.
- **The agent jar:** a git clone has none (`*.jar` is in `.gitignore`). With the project's source there, the installer runs `java-agent/build.sh` every time, so an update never installs an old jar. If that fails, it warns and installs the jar that's already there; with none at all it stops and names a JDK to install.

- **For you or for all.** By default for the user, without root (`~/.local/share/iKVM-KeyPasta` for the agent and the starters, `~/.local/share/applications`, `~/.local/share/icons`, `~/.local/bin/ipmiview`). `--system`: for all users, as root (`/opt/iKVM-KeyPasta`, `/usr/local/share/applications`, `/usr/local/share/icons`, `/usr/local/bin/ipmiview`), so that no user can change what the others run; IPMIView then comes only from `/opt/SUPERMICRO`, `/opt`, `/usr/local/share`, `/usr/share` or a download in the current folder or `~/Downloads`, and is unpacked or copied into `/opt` (made readable for all): other users can't read the installing user's home folder. Installing one kind removes the other. The viewer runs as the user on Linux, so a copy in the home gives nothing away (unlike Windows, where it runs as admin).
- The menu entries: `IPMIView.desktop`, `iKVM-Viewer.desktop` (the program for `.jnlp` files; it also gives the viewer's windows their name and icon, whether started from IPMIView or a `.jnlp`) and the icon in all sizes, with the install's paths filled in. The entries name their icon by its full path: WSLg (Linux apps in Windows' Start menu and taskbar) finds icons by name only in `/usr/share`, and showed blank ones otherwise. WSLg lists only the entries for all users (`/usr/local/share/applications`), not those in `~/.local/share/applications`. Making iKVM Viewer the program for `.jnlp` files (`xdg-mime default`) is asked first: Enter means yes if none is set or it's OpenWebStart's (or javaws or IcedTea-Web), else no; `--jnlp` sets it without asking, `--no-jnlp` leaves it, and so does a run without a terminal to ask in. If it isn't set, the installer says how to do it by hand.
- `ipmiview-keypasta.sh` sets `JAVA_TOOL_OPTIONS` for IPMIView only (the viewers it starts inherit it) and starts IPMIView.
- **IPMIView's settings in `~/.config/ipmiview`** (`$XDG_CONFIG_HOME`). IPMIView's settings (`IPMIView.properties` with the BMC list, `account.properties` with saved IDs and passwords, a few more `*.properties`) are kept there, the same for every IPMIView version, and IPMIView's own folder stays as unpacked (for all users a normal user couldn't write it anyway). IPMIView runs in its own folder (it finds its files relative to the folder it runs in) and is given the settings folder as its argument (`IPMIView20 - <folder>/`); the agent sends the settings files IPMIView still opens in the folder it runs in there too (section 7). A settings file missing there is copied from IPMIView's folder as a starting point (e.g. a BMC list prepared there), `account.properties` only from an IPMIView folder the user owns: saved passwords are personal. (The Mac script does the same with `~/Library/Application Support/IPMIView`.) Without the jar, or with a space in its path (`JAVA_TOOL_OPTIONS` can't quote it), IPMIView starts without the agent rather than not at all. IPMIView's folder: an argument, else the newest `IPMIView*` folder in the places above.
- **`jnlp-keypasta.sh`** works like the Windows jnlp launcher (no admin rights needed on Linux): an iKVM `.jnlp` (one naming `tw.com.aten.ikvm`) is started with the agent for this start only, from a copy in `~/.cache/iKVM-KeyPasta/launch-<date>-<time>-<BMC>-<random>.jnlp`, readable by the user only (it holds the console session's login data), and kept there for a week after it was last opened, then deleted at the next start, with what was fetched for it (`~/.cache` is never cleared by itself). The original in Downloads is removed only once a viewer window has opened (the agent's file, see the Windows launcher), compared by `cksum` taken before the copy is changed (`VIEWERWAIT`, 300 s; with IcedTea-Web, whose `javaws` runs the viewer itself, also given up as soon as it ends); otherwise it stays and a notification says so. Any other `.jnlp` goes to `javaws` unchanged. Started without a file: the newest `launch*.jnlp` in the Downloads folder (`launch (1).jnlp` and so on). `javaws`: `$JAVAWS`, else OpenWebStart's in `~/openwebstart` or `/opt/openwebstart`, else the one in `PATH` (often IcedTea-Web's: Debian/Ubuntu `icedtea-netx`). Which one it is, is told by its real path (`readlink -f`: OpenWebStart's has "openwebstart" in it). With `--debug` the log is followed until Ctrl+C, as OpenWebStart may hand the viewer to a JVM of its own and return.
  - **OpenWebStart:** Java 8 asked for in the copy (`JAVAVERSION`), the agent in `JAVA_TOOL_OPTIONS`; OpenWebStart downloads the jars and the Java itself.
  - **IcedTea-Web,** as in the Mac app's container (section 13): its `javaws` panicked ("thread 'main' panicked at src/os_access.rs", the Rust one; Debian, Ubuntu and others also have a shell one) when the Java it settles on doesn't exist: `deployment.jre.dir` in `~/.config/icedtea-web/deployment.properties` (shared with OpenWebStart, a fork of IcedTea-Web, which keeps its own settings there), else `JAVA_HOME`, else the Java it was built for. So IcedTea-Web gets a profile of its own: `XDG_CONFIG_HOME` set to `~/.config/iKVM-KeyPasta/icedtea-web` (its settings and the publishers you chose to trust in `icedtea-web/` there), `deployment.jre.dir` written there on each start, and `JAVA_HOME` (the shell `javaws` takes that first); the agent keeps its own settings folder (`KEYPASTA_SETTINGS_DIR`). Its Java: `ITWJAVA`, else the newest Java 11 in `/usr/lib/jvm` (also `/usr/lib64/jvm`, `/opt/java`, `~/.jdks`), else the newest of 9 to 23 there (said so): IcedTea-Web needs 9 or newer (current packages are built against it) and the security manager, gone in 24; the viewer is tested on 11. The jars: BMCs serve them Pack200-compressed only, which IcedTea-Web no longer unpacks, so `keypasta-jnlp-jars` (the container's, installed next to the launcher) fetches them beforehand into `launch-...-jars/` next to the copy, unpacked with that Java's `unpack200` (Java 13 and older; else any such Java's), and writes `launch-...-local.jnlp` loading them from there (its codebase that folder, no `href`: IcedTea-Web would fetch the `.jnlp` again from there). It needs `python3`. The viewer runs in IcedTea-Web's own JVM (`-Xnofork`, `-nosecurity`), the agent given there with `-J-javaagent:` (one argument: a space in the jar's path is fine); a `JAVA_TOOL_OPTIONS` of your own is moved onto the command line the same way, as the shell `javaws` reads the Java version from the first line `java -version` prints, and "Picked up JAVA_TOOL_OPTIONS" comes first. `--debug` also gives IcedTea-Web `-verbose`.
- **`libnsl.so.1` for encrypted consoles.** The stunnel the viewer brings (`res/linux/stunnel64` in the `.jnlp` viewer's jar; IPMIView's `BMCSecurity/linux/stunnel64` is likely the same) is linked against `libnsl.so.1`, an old glibc library. Debian and Ubuntu still have it in glibc; Fedora and others ship it as a package of its own (`libnsl`). Without it stunnel exits at once (127, the loader), the viewer's connection to its local tunnel port is refused, and all it says is "connect failed sd:N". Both starters check for it (`ldconfig -p`) and say what to install; the `.jnlp` one also as a notification. They start anyway (a console without encryption doesn't need it).
- **Window classes.** A desktop ties windows to their menu entry by their window class (`StartupWMClass`): name and icon in the dock, windows grouped. Java takes the class from where its window system was started: IPMIView's own launcher gave "com-zerog-lax-LAX", with the agent "java-lang-Thread", meaningless either way. The agent sets "IPMIView" and "iKVM-Viewer" right after Java's window toolkit starts, before the first window.
- **The command `ipmiview`:** a link to `ipmiview-keypasta.sh` (in `~/.local/bin` or `/usr/local/bin`, see above; most systems put `~/.local/bin` into `PATH` once it exists). An `ipmiview` that isn't this link is left alone. The starters follow links to find the agent next to themselves; a bare `ipmiview` finds IPMIView as the menu entry does.
- **`--debug`** (`-d`), when started from a terminal: the agent logs to `~/.local/state/iKVM-KeyPasta/agent.log` (the run before: `agent.log.old`), and the script shows it there as it grows, next to IPMIView's own output, until IPMIView ends. A file rather than the terminal itself, because IPMIView starts the viewers with their output connected to IPMIView, not to the terminal; the viewers inherit the agent's options and write to the same file. Not `/var/log`: only root may write there.
- `bash linux/install.sh --remove` (or `--uninstall`) removes all of it; IPMIView's folders stay.

## 13. macOS: the app, the scripts, the container

Supermicro offers no working Java console for macOS: IPMIView (2.25) refuses the KVM console there for BMCs with encrypted KVM ("The function can't support on mac"), and the `.jnlp` viewer needs an Intel Java and OpenWebStart. The `mac/` folder makes both work, with the agent.

### The app (`mac/launcher-app`)

`IPMIView+iKVM KeyPasta launcher.app`, called iKVM-KeyPasta in its window and menus, starts IPMIView or a dropped `.jnlp` with the agent, and shows their output in its window. Everything on the Mac (app, scripts, container) has only been tested on macOS 27.

- **Build and install:** `build.sh`, with the Xcode Command Line Tools only (no full Xcode). It builds a universal app (Apple silicon and Intel) for macOS 13 and newer, whatever macOS builds it (13 for SwiftUI's single-window scene; anything newer is used only where available); 13 to 26 are what it's built for, not tried. Its `java-launcher` stays Intel only, like the viewer's Java. The agent jar is bundled in the app: `build.sh` runs `java-agent/build.sh` first every time the project's source is there; if that fails, it warns and bundles the jar that's already there, with none at all it stops. `JAVA_TOOL_OPTIONS` can't quote paths with spaces, and the app's name has one, so the app uses the jar from a copy in the temp folder.
- **`build.sh --install`** then puts the app into `/Applications`, or `~/Applications` when `/Applications` isn't writable for the user: admins may write there without sudo, so no elevation is asked for. An app already there goes to the Trash first, moved there by the system: macOS 15's `trash` command, on older macOS its trash function (`FileManager.trashItem`) called through `osascript`'s JavaScript, which needs no Finder and so no permission prompt; if it can't be moved, the new one stays in `mac/launcher-app/`. A running copy keeps running until quit. The new app is registered with Launch Services right away, for `.jnlp` files.
- **One fixed identity for macOS's permissions.** Local Network and the firewall are granted to this app once; the viewers and the tunnel run as its children and count as the app, so nothing asks again.
- **The viewers are its children:** quitting the app ends them and their sessions, so it asks first while any is running.
- **`.jnlp` files** run through OpenWebStart's own engine (IcedTea-Web) with a separate profile of the app's, in the app's process tree: OpenWebStart's macOS launcher ignores a file passed to it and forks a detached process. An iKVM `.jnlp` (one naming `tw.com.aten.ikvm`) is handled as by the Windows launcher (section 11): copied to `~/Library/Caches/iKVM-KeyPasta/launch-<date>-<time>-<BMC>-<random>.jnlp`, readable by you only, and kept there for a week after it was last opened (opened again, it works as long as the BMC accepts that login; sessions live long, and even an expired one can help). Older copies are deleted whenever a `.jnlp` is opened (macOS clears `~/Library/Caches` only when the disk runs low). The original in Downloads is removed only once a viewer window has opened from the copy, and only if it's still the same file; the app waits up to 300 seconds for that (fixed, not a setting). Any other outcome leaves the original where it was for another try. Removing it lets the browser save the next one under the same name, and the file, which holds the console session's login data, doesn't stay in Downloads. Natively the app checks for the agent's file next to the copy (the viewer is the app's own Java process: its end without the file ends the wait), in a container for `/tmp/viewer-opened` there (`entrypoint.sh` sets the variable; `docker exec`); the log pane says whether it was removed or kept. Other `.jnlp` files stay where they are.
- **Status dot:** green everything works as it should, yellow with a shortcoming, orange only IPMIView or only `.jnlp` files, red nothing.
- **About and Help:** the app menu's About shows a short notice of what the app is (and that it isn't Supermicro's or ATEN's) and a link to the project page; Help › "iKVM-KeyPasta on GitHub" opens that page (there's no help book).
- **One window,** no File › New Window and no tabs; File › Open .jnlp… (`Cmd+O`) opens a `.jnlp`, as the drop area does. While IPMIView or a `.jnlp` starts, a throbber takes the place of the button's symbol: until its window is there (natively: the app named "IPMIView" or "iKVM Viewer" appears, see `java-launcher`) or its console answers (container), 90 s at most.
- **Open Downloads/…** names the newest `launch*.jnlp` in `~/Downloads` (by modification date). The app watches the folder (a browser saves under a temporary name or in a `.download` folder and then renames or moves the file: each changes the folder) and looks again 0.3 s after a change, and whenever it comes to the front.
- **Container mode** (see below), for when the native viewer can't run. While IPMIView's container runs, the launch button opens its console instead (starting it again would replace the container and end IPMIView and its viewers); Stop is next to it in the list of running containers.
- **Finding IPMIView** (the app when its IPMIView folder is empty or auto-detected, `ipmiview-keypasta.sh` and `container/run.sh` without a folder given): an `IPMIView*` folder with `IPMIView20.jar`, also one folder down (`~/Applications/IPMIView/IPMIView_2.25.0_.../`), in the first of `~/.local/share`, `~/.local/bin`, `~/Applications`, `/opt`, `/Applications` that has one, and there the newest by the version in its name (its numbers from the first digit on, compared as numbers: 2.25 is newer than 2.9). Not `~/IPMIView*`.
- **Preferences** in three tabs: General (IPMIView folder, Run in Native | Container, Accept expired firmware certificate), Native (viewer Java, OpenWebStart) and Container (engine, Consoles, a tab or window per viewer, the container's keyboard layout, folders, security). The paste hotkey, the remote's layout and the Alt/Command swap are the viewer's own, per BMC, in its Options › KeyPasta Preferences. Native before Container, as in Run in. Each tab has the status dot top left (the main window's); on the tab of the mode not chosen it's grey: "Not used: the consoles run in the container" (or natively). Settings the containers take at their start: a tab per viewer (IPMIView's container only) is locked from the click that starts IPMIView's container (its build included) until it ends, security (password, localhost) while any container starts or runs, each with "Can't change while container is running."; the container's keyboard layout and the folders stay changeable, with "Does not apply to running containers." while any starts or runs. The taskbar (tint2) on IPMIView's desktop is there only with a tab per viewer off, to switch between the viewers' windows.
- **Where the consoles open** (Preferences › Container › Consoles): in the **VNC app** if there is one, else in the **browser**; Option-click a console's Open console button (or the launch button) for the other one, its label says which while Option is held. IPMIView's iKVM viewers (each in a tab of its own) open the way IPMIView's console was opened last (remembered across restarts), so an IPMIView opened in the browser with Option-click gets its viewers in the browser too. The window lists what runs, grouped: **IPMIView** (its container, and below it each viewer in a tab of its own, by its BMC: the container's `/tmp/viewer-names/N`, written by the viewer-tab script; Stop ends that viewer only, as its desktop menu's "End this console") and **.jnlp** (its consoles). VNC app: Automatic (TigerVNC Viewer if installed, else none), None (the browser), TigerVNC Viewer, an app chosen with "Select other…" (`open -a APP vnc://127.0.0.1:PORT`), or a custom command with `HOST` and `VNCPORT` in its environment (`"vnc://${HOST}:${VNCPORT}"` appended if it uses neither; example: `open -na "TigerVNC Viewer" --args -FullScreen "${HOST}::${VNCPORT}"`). Browser: Automatic (Chrome or Edge, whose fullscreen passes Ctrl+Tab and Alt+Tab to the remote, else the default browser), the default browser, one of the browsers macOS knows for web pages, another chosen with "Select other…", or a custom command with `URL` (`"${URL}"` appended if missing; example, Chrome's profile "Profile 1" in app mode: `open -na "Google Chrome" --args --profile-directory="Profile 1" --app="${URL}"`). The commands run by `/bin/sh`, the variables quoted as written. The engine shown as in use is run.sh's: podman without a docker command, else the engine whose socket is there, else the one run.sh would start.
- **Security** (Preferences › Container): "This Mac only" (on: run.sh publishes the ports on 127.0.0.1; off: `--lan`, all addresses) and "Accept any VNC password" (on: no password, VNC apps may give any; off: the password). Off this Mac, a password is a must: anyone who reaches the Mac would get IPMIView with its saved BMC logins, so "Accept any" is switched off then, and run.sh refuses `--lan` without one. The password goes to run.sh in its environment only (`VNC_PASSWORD`, then `docker run -e VNC_PASSWORD`: on no command line, in no log); in the container `entrypoint.sh` makes an Xvnc password file of it (`tigervncpasswd -f`), removes it from the environment, and starts the desktops with VncAuth: VNC apps and the browser view (noVNC) ask for it; keypasta-vncauth only relays then (`--relay`). VNC keeps the first 8 characters. The app keeps it in `~/Library/Application Support/iKVM-KeyPasta/vnc-password`, readable by the user only (not the Keychain: the app is signed ad hoc, so every new build would be asked for it again). For containers started afterwards.

### `ipmiview-keypasta.sh`

The script the app runs for IPMIView (also usable alone). It starts IPMIView with the agent, which turns IPMIView's own Mac code for the encrypted console back on (section 7); without the agent, that console doesn't open. IPMIView's files stay unchanged. It also:

- renames the Linux package's `jre` folder to `jre-linux` (else IPMIView looks for the viewer's Java there);
- puts a small `stunnel` wrapper into `BMCSecurity/mac/` that starts Homebrew's stunnel (IPMIView copies its tunnel program to a new temp folder for every console, and a copied program makes the firewall ask every time);
- sets `proxy_ip=127.0.0.1` in `stunnel.properties` (else the tunnel listens on the network address, which the firewall asks about too);
- keeps IPMIView's settings (`IPMIView.properties` with the BMC list, `account.properties` and a few more) in `~/Library/Application Support/IPMIView`, given to IPMIView as its settings folder (and to the agent, section 7), so they stay apart from IPMIView and survive an update; a settings file missing there is copied from the IPMIView folder once.

The viewer needs an **Intel Java 8 or 11** (it loads x86_64-only native libraries; on Apple Silicon it runs through Rosetta 2; newer Javas refuse the `.jnlp`'s Java options), IPMIView itself runs on any. The app looks in `/Library/Java/JavaVirtualMachines` for an Intel Java (by `OS_ARCH` in its `release` file; one without that file counts after the Intel ones, an Apple silicon one never): 11 first, then 8, else any; Preferences › Native sets another. The encrypted console needs **Homebrew's stunnel**. stunnel's log: `/tmp/iKVM-KeyPasta-stunnel.log`.

### `java-launcher` and the names in the Dock

The Dock and Cmd-Tab name a program without an app bundle by its executable's file name: "java" for every Java program (Java's `-Xdock:name` reaches only the menu bar since OS X 10.9, an open OpenJDK bug). So `java-name.sh` (first in `PATH` as `java`, since IPMIView starts the viewers as `java`) runs IPMIView through a copy of `java-launcher` named "IPMIView", and the viewer through one named "iKVM Viewer"; anything else as plain java. `java-launcher` starts Java inside its own process. The two copies live in `~/Library/Application Support/iKVM-KeyPasta/Launchers`, replaced only when they change: two programs for the firewall, asked about once.

`java-launcher` also carries the agent's only native code, the menu bar watch for macOS 27 and the Cmd+Q shortcut removal (see [6](#6-the-java-agent-fixes-in-the-ikvm-viewer)): Java finds a JNI library built into the program it runs in, so that needs no file of its own.

### Container mode (`mac/container`)

The whole console in an amd64 Linux container, shown in the browser (noVNC) or a VNC app. Engines: OrbStack, Docker Desktop, Colima or Podman (Colima is an engine without Docker Desktop that needs Homebrew's `docker` command; Podman has its own `podman` command, which `run.sh` uses when there is no `docker`; a missing Podman VM is made with `podman machine init`). Colima and Podman share only the home folder (and a few others) with their Linux VM, so `run.sh` puts what it mounts from elsewhere into `~/Library/Application Support/iKVM-KeyPasta/container` first: the agent jar (the app's copy in the temp folder, `/var/folders`, came out as an empty folder there, and the agent wasn't loaded) and a `.jnlp`, a copy per container, replaced whole so a running one keeps its own. An IPMIView, virtual media or screenshots folder outside the home folder gets a note (it may be empty in the container).

**Reaching the BMCs** is the engine's business, not checked by the app. Colima's user-mode network (and likely Podman's) runs in a helper program that macOS's Local Network permission silently denies (macOS 15 on), so every BMC connection was refused while the Mac itself reached it; `colima start --network-address` (a root helper, which the permission doesn't apply to) or the permission granted fixes it, and `--vm-type vz --vz-rosetta` replaces QEMU's x86 emulation with Rosetta. `bmc-check HOST` in the container (`docker exec ikvm-console bmc-check 192.0.2.40`) shows whether a BMC answers there (UDP 623 IPMI, TCP 623/5900/443/80) and how x86 code runs.

**The image:** Ubuntu 26.04 (standard support to 2031) with Ubuntu's Java 11 runtime, which IPMIView, the viewers without a JRE of their own, IcedTea-Web and the `.jnlp` viewer in it run on (`JAVA_HOME`, the `java` alternative). Not Java 8: 26.04's IcedTea-Web calls a Java 9 method at its start (`URLConnection.setDefaultUseCaches(String, boolean)`: "NoSuchMethodError", the `.jnlp` window closed at once). Not newer: the viewer's `.jnlp` asks for options Java 17 refuses, and IcedTea-Web needs Java's security manager, removed in Java 24; Ubuntu's IcedTea-Web package also installs the default Java (25), which isn't used. IcedTea-Web's start scripts read the Java version from `java -version`, whose first line was the "Picked up JAVA_TOOL_OPTIONS" note with the agent set ("integer expected", and Java 9+'s module options left out): the image runs that check without the variable. The BMC serves the `.jnlp`'s jars Pack200-compressed only (`NAME.jar.pack.gz`; `NAME.jar` is 404). This IcedTea-Web can't unpack those (Java dropped Pack200 in 14) and loaded nothing ("Unknown Main-Class"; asking it for the plain jars instead got the 404). So `keypasta-jnlp-jars` fetches this Linux's jars (the viewer, its native library) from the BMC first and unpacks them with Java 11's `unpack200`, and IcedTea-Web starts a copy of the `.jnlp` that loads them from the container (a plain `.jar`, if a BMC has one, is taken as it is). Old, unnamed builds of the image are removed on every container start (`docker image prune` for the image's label only). noVNC is 26.04's 1.6.0, its files only (the package pulls in Node.js). noVNC 1.6 keeps CapsLock in step itself: when the container's CapsLock differs from the Mac's, it sends a CapsLock first (it knows the container's from TigerVNC's LED messages). The image is rebuilt only when the container folder's files changed: their checksum is kept in the image as a label (`ikvm-keypasta.files`), so a rebuilt app with the same files reuses it.

***Why* a container:** the viewer's native libraries are x86_64 only; macOS 28 removes Rosetta 2 for Mac apps (keeping a subset for older games), and then only a Linux container can run them. On a Mac every container engine runs its containers in a Linux virtual machine (containers share the kernel, and macOS has no Linux kernel), and the x86 code there is translated again: by Rosetta for Linux where the engine and macOS still offer it (OrbStack; Colima with `--vz-rosetta`; whether macOS 28 keeps it is not known yet), else by QEMU emulation, much slower. So the container needs far more memory and CPU than the native start did. On Linux, IPMIView's own encrypted console works as it is.

**Using it:** the app builds the image on first use and opens the console when it's up. The browser view's address is plain, `http://localhost:PORT/`: connecting at once and the desktop following the window's size are noVNC's own settings (`mandatory.json`, `defaults.json`). Folders for virtual media images and for screenshots/recordings can be mounted; fonts are antialiased (over VNC, Swing looked awful without). IPMIView's main window fills the desktop without a frame (a window manager rule for its window class; the agent then leaves its size alone).

**Settings shared with the native start:** the BMC list (`IPMIView.properties`) and the saved logins (`account.properties`) are the ones in the Mac's `~/Library/Application Support/IPMIView`, mounted at `/settings`; IPMIView runs in `/ipmiview-work`, a folder of links to its program (`/ipmiview`) and to those settings. The `.jnlp` start's settings and the certificates you chose to trust ("Always trust content from this publisher") are kept too, in the Mac's `~/Library/Application Support/IPMIView/icedtea-web`, so you're asked once per publisher, not on every start. Not in OpenWebStart's `~/.config/icedtea-web`: that holds Mac paths and OpenWebStart's own choices. The agent's settings (its KeyPasta dialog) are the native start's own file, `~/Library/Application Support/iKVM-KeyPasta/agent.properties`, mounted at `/keypasta-settings`.

**The desktop:** the window manager (openbox) has no key bindings, so every key goes to the remote (its standard ones took Alt+Tab, Alt+F4, which closed the console, Ctrl+Alt+arrows and others); the mouse and the desktop menu do the rest. The desktop menu (right-click) opens IPMIView, IcedTea-Web's settings (Java Web Start's settings and certificates; open-source Java has no other Java control panel), or restarts the container.

**A `.jnlp`'s container and a viewer's own tab are alike:** the viewer's main window fills the desktop without a frame (only it: matched by window class and its opening title "Java Viewer"; IPMIView's own main window by "IPMI*View*", not its SOL, Trap Receiver or keyboard windows), its other windows keep their frames, no window list (every iKVM viewer looks the same, from IPMIView or a `.jnlp`; only IPMIView's desktop has one, tint2, and only when its viewers have no tab of their own), and the desktop menu (right-click) has "End this console" (the viewer's tab: ends that viewer, TERM then KILL after 3 s; the `.jnlp`'s: ends the container) and, for a `.jnlp`, IcedTea-Web's settings.

**One IPMIView container, any number of `.jnlp` ones** (up to 99): IPMIView's is `ikvm-console` on port 6100, a `.jnlp` gets a container of its own, `ikvm-jnlp-PORT` on the first free port of 6201–6299, next to it and the others, and its tab is titled "iKVM <BMC>" (the `.jnlp`'s first argument). Its viewer fills the desktop without a frame, as in a viewer's own tab (window manager rule for its window class and the title it opens with, "Java Viewer", so only the main window: its virtual keyboard, preferences and macro windows keep their frames; `KEYPASTA_VIEWER_TAB=1` for the agent); IcedTea-Web's dialogs stay windows. It ends with its viewer and is removed then (a closed viewer or a cancelled start); its desktop menu has "End this console" instead of a restart. The app lists the running ones (IPMIView's too) with Open console (Option-click: the other view) and Stop, and notices every 5 s which ended. At its start it finds the containers already running (IPMIView's restarts with the engine; the app may have quit while they ran) and lists them; IPMIView's viewer tabs are watched again, without reopening those already up. An engine that isn't running isn't started for that.

**On this computer only, and a VNC app too.** The ports are published on `127.0.0.1` only, unless Security (above) allows others, which needs a password: otherwise anyone on the network could use IPMIView and its consoles. Next to the browser view each desktop is there for a VNC app on the web port − 400; the last two digits are the desktop's number in both:

| Number | Desktop | Browser | VNC |
|---|---|---|---|
| 0 | IPMIView | 6100 | 5700 |
| 1–99 | viewers IPMIView opens, each on a desktop of its own | 6101–6199 | 5701–5799 |
| 1–99 | `.jnlp` consoles, a container each | 6201–6299 | 5801–5899 |

59xx is left alone: 5900 is macOS's own Screen Sharing, 5901 and up are the usual ports of other VNC servers. In the IPMIView container the viewers' desktops use the same ports as on the Mac (not 6080 + n: 6000–6099 are X11's TCP ports); IPMIView's own desktop is 6080/5900 inside. Docker Desktop and Colima forward each published port on its own, so the IPMIView container with viewer tabs (200 ports) starts a little slower there. Preferences › Container › Consoles, VNC app: "Automatic" or "TigerVNC Viewer" opens the consoles there instead of the browser when it's installed (`brew install --cask tigervnc-viewer`; without it the browser): no browser between the keys and the container (no shortcuts kept by the browser, no clipboard permission questions; TigerVNC shares the clipboard itself), the whole keyboard in its fullscreen. The VNC port is `keypasta-vncauth` (python), in front of Xvnc, which listens on the container's loopback only (15900, 15700 + n; the browser view's websockify connects there directly). It offers None first and then VNC authentication that takes any password, empty too: a client picks the first type it supports from the server's list, so TigerVNC Viewer connects without a question, and a VNC app that insists on a password can give any. No less safe than no password at all: without a password the ports are this Mac's only (Security, above). After the handshake every byte goes through unchanged; connections are logged in the container's `/tmp/vncauth*.log`.

**noVNC is served with "Cache-Control: no-cache"** (`keypasta-websockify`: websockify with that header). Browsers keep pages without that header for a time they guess from the file dates: after the image changed to noVNC 1.3.0, one kept 1.0.0's `ui.js` and ran it with the new page ("Cannot read properties of null (reading 'addEventListener')"). With the header the browser asks each time (unchanged: a short "304").

**Keys, from the Mac to the remote.** Each layer passes a key on by its place, not by its character, so the remote's own layout makes the character:

1. *macOS → browser:* the browser gets the key's place (`code`) and its character. macOS and the browser keep some shortcuts (Cmd+Tab, Cmd+Space, Cmd+Q; Cmd+W, Cmd+T in a tab). In noVNC's fullscreen the page locks the keyboard where the browser can (Chrome, Edge: Keyboard Lock): most of those go to the remote then; hold Esc to leave fullscreen.
2. *browser → noVNC* (`keypasta.js` first, then noVNC): on an ISO keyboard macOS gives the key left of 1 and the key left of Z each other's place, and some browsers pass that on; told apart by the character as the agent does natively (§ ° ± ¶ • \` ~ ^ ¬ and dead keys are left of 1). macOS sends no release for a key pressed with Command held (the remote kept it down: with Alt and Command swapped, Cmd+C left C repeating): released when Command goes up. noVNC's own swap of Option and Command for a Mac (Command as Alt, Option as AltGr) is taken out of the image: Command is the Windows key, Option Alt, as natively; the agent swaps them per BMC if asked (see [3](#3-keys)).
3. *noVNC → Xvnc:* noVNC sends each key's place (QEMU extended key event) and a character. Xvnc went by the character, giving a key the container's layout lacks (ö, é, §) a made-up key code, which the agent can't place: nothing reached the remote. With `RawKeyboard=1` it goes by the place.
4. *Xvnc → Java:* the container's layout is the Mac's (the app passes its current input source, `--layout`, the PC variant: right Option is AltGr), so typing into IPMIView's own fields there gives the same characters as on the Mac.
5. *Java → agent → remote:* the agent sends the place (X key code), see [3](#3-keys).

A paste hotkey with Command (`cmd+shift+V`) in the container: Command arrives as the Windows key (Super), which X gives Java no modifier for, so the agent would see Shift+V only and type a V. So the agent (Linux) counts a held Windows key as Command for the hotkey. In the browser view `keypasta.js` also kept the hotkey's V as "swallowed" for good (macOS sends no release for a key pressed with Command held, and its own release fix never saw that V): it lets go of it when Command goes up.

**Clipboard, shared both ways** (`keypasta.js`): copied in the container (its clipboard, not a mere selection: Xvnc `SendPrimary=0`, a selection used to land in noVNC's clipboard panel) goes to the Mac's clipboard (Chrome and Edge while the page has the focus, else when it gets it back); the Mac's goes to the container's whenever the page gets the focus, once reading it is allowed (Chrome and Edge ask once, at the first paste hotkey). Not on focus in Safari and Firefox: they would ask every time; the paste hotkey works there anyway.

**Viewers in browser tabs** (the app's "Each iKVM Viewer in a tab or window of its own", on by default; a TigerVNC window each when the consoles open there): each console IPMIView opens gets a desktop of its own (up to 99), filled by the viewer's window without a frame, and the app opens it in a new browser tab, titled "iKVM <BMC>"; the tab's desktop follows the tab's size. How: IPMIView starts its viewers as `./jre/bin/java -jar iKVM….jar` in the folder it runs in; there `jre/bin/java` is a small script that starts a desktop (Xvnc on display 1–99) with its own window manager and browser connection (ports 6101–6199, VNC 5701–5799, published by `run.sh`), runs the viewer there, and removes it all when the viewer ends; anything else goes to the real Java. The app polls those ports while the container runs (up to 3 above the highest one up: a new viewer takes the lowest free number) and opens a tab for each that comes up. Each viewer is a Java of its own plus its desktop, a few hundred MB, more under emulation (see the container's *Why*). The viewer resizes its own window on connecting and on every new resolution, which would undo the maximizing: with `KEYPASTA_VIEWER_TAB=1` (set by that script) the agent keeps the window maximized and resizable and leaves out its other size fixes. A closed viewer leaves its tab on noVNC's "disconnected" page: browsers don't let a page close a tab it didn't open. What it does is in the container's log (`docker logs ikvm-console`): a line per viewer started and ended, with its port.

### Expired iKVM certificate

Old BMC firmware ships an iKVM TLS certificate with a fixed expiry (X10 AST2400 firmware 03.93: 17 May 2026). After that date the stunnel log shows `certificate has expired` and the console won't open. The HTML5 viewer still works (it doesn't use this certificate), but it can't mount a remote ISO.

The tunnel is mutual TLS: the BMC presents its certificate *and* requires the client's, and both expired the same day. Without changing the firmware, two steps together:

1. The app's "Accept expired firmware certificate" (Preferences › General) (`IGNORE_EXPIRED_CERT=true` for the script): the tunnel stops checking the BMC's certificate (`verify = 0`). The console stays encrypted, but the BMC's identity isn't checked, for every BMC opened that way: leave it off otherwise.
2. Set the BMC's clock back before the expiry (NTP off, date set in Configuration › Date and Time, or `ipmitool ... sel time set "01/01/2025 12:00:00"`), because the BMC checks *our* expired certificate against its own clock. SEL timestamps are wrong meanwhile.

Newer firmware (04.07) has certificates valid to 2041; updating the BMC is the lasting fix.

### Karabiner-Elements rules (`mac/karabiner-elements`)

Optional, each for the Java iKVM Viewer and for TigerVNC Viewer: `swap-fn-fkeys-*` makes F1–F12 reach the remote without fn (fn then gives the media keys); `swap-alt-cmd-*` swaps Alt and Command, made before the agent could do that itself (see [3](#3-keys)).

### Icons (`mac/icons`)

Light and dark `.icns` and SVGs, including layers for Icon Composer (an `.icns` can't follow dark/light mode, and macOS 26 puts icons that aren't rounded squares into a grey square unless they come from Icon Composer). The 16 and 32 pixel sizes use Apple's classic format, not PNG: small list views (e.g. System Settings' privacy lists) showed PNG there as colored noise.

## 14. Logs and diagnosis

- **Agent:** `log=<file>`. Decisions only, never typed keys or passwords. Linux launcher with `--debug`: `~/.local/state/iKVM-KeyPasta/agent.log`. Mac app: off; `debugLogs = true` in `IPMIViewKeyPasta.swift` (and a rebuild) writes `~/Library/Logs/iKVM-KeyPasta/agent.log`, runs IcedTea-Web with `-verbose` (natively, and in a `.jnlp` container: `run.sh --debug`) and keeps an ended `.jnlp` container's whole output there (`jnlp-console-N.log`); without, the app's log shows that output's last 40 lines.
- **stunnel on macOS:** `/tmp/iKVM-KeyPasta-stunnel.log`.
- **Is it active?** The viewer's title (Java) or tab title (HTML5) ends with ⌨.
- **AutoHotkey:** `DebugMode` (see [10](#10-the-autohotkey-script)).

## 15. Tried and dropped

Kept here so nobody tries them again without a new reason.

- **A stand-in for IPMIView's `StunnelFacotry` on the class path** (macOS, until 2026-10): a copy of the whole class, compiled on the first start against `IPMIView20.jar` (else a prebuilt one). It hid every later change of that class, Mac support of IPMIView's own included, failed obscurely without a JDK once the classes it called changed, and wasn't recompiled when IPMIView was updated in place. The agent does it now (section 7).

- **The agent's jar from an environment variable** (Windows launchers): any program running as you could set it and choose what runs as admin. The launchers take the jar only from their own folder or the one above.
- **The agent into the viewer's own elevated restart** (Windows, `.jnlp`), so the launcher needn't elevate: see section 11, "Why the jnlp launcher elevates first".

- **Other ways of sending CapsLock** (see [3](#3-keys)): both codes per press, "on" then "off" per press (each left a text console or an X desktop stuck on), keeping the agent's own idea of the remote's state, following the BMC's LED reports (it sent none), and a menu to toggle a lock (two codes back to back: the BMC took only the first, so it could only turn a lock on).
- **macOS's Input Monitoring permission** for the keyboard LEDs (the app used to ask for it): it had to be granted again after every update, and it only made the Mac's LEDs follow the remote's, on BMCs that report them. The agent leaves out the LED calls instead.
- **macOS's Screen Sharing as the container's VNC app:** it never got past "connecting", with no error, so it isn't offered. The VNC port's any-password option was made for it and stays for other VNC apps.
- **macOS, menus after Record's dialogs:** asking for the focus repeatedly and bringing the window to front (no effect: macOS had it as key already); a focus round trip through an invisible 1×1 window (keys came back, the menus disappeared: that window took the menu bar, and the viewer, still the main window, didn't get its menus back); handing the window its menu bar again (no visible effect on macOS 27); removing a stuck native dialog block (never happened). See [6](#6-the-java-agent-fixes-in-the-ikvm-viewer) for what works.
- **macOS, redrawing the menu bar at guessed moments** (until 2026-10, agent 3.4): after the focus came back to a window, after IPMIView's start, on every focus gain. Menus still went missing often; the native menu bar watch (section 6) redraws when the menus actually change.
- **WSLg:** `_JAVA_AWT_WM_NONREPARENTING` (didn't change the frame sizes); restoring "resizable" right after the viewer turned it off (too late).
- **Fonts on macOS:** loading San Francisco from its file (drawn heavier than native text); Helvetica 11 (too small).
- **Dock names:** one launcher copy per BMC (one firewall rule each); app bundles (the Dock still showed the executable's name); setting LaunchServices' display name from inside Java (only Force Quit and Activity Monitor followed).
- **Input methods off on macOS:** every mouse movement got slow.
- **IPMIView's own-address lookup:** caching the first answer (could go stale when a network adapter goes away; the loopback address needs no lookup at all).

## 16. Known issues

As of October 2026.

**Open problems**

- **macOS: CapsLock sometimes toggles twice** (native viewer and container, cause not found). In the container, noVNC also sends a CapsLock of its own when the remote's CapsLock light and the browser's differ.
- **The remote's CapsLock state isn't known to the viewer:** the BMC seen so far never reports its keyboard lights. iKVM sends CapsLock as the local state (see [3](#3-keys)), so when the remote's CapsLock differs from the local one, the first press only brings them in step and seems to do nothing. Windows and Linux have the setting "Caps Lock: Simplified" for consoles that lose every second CapsLock.
- **macOS 28 and later can't run the native console:** the viewer contains Intel-only code, which macOS 28 no longer translates for Mac apps. Container mode works there (see [13](#13-macos-the-app-the-scripts-the-container)).
- **IPMIView's own text:** its note after File › Save lacks a space before "are *.properties files" (its language file; the agent only fixes the folder name and "save" → "saved").

**Built and checked by machine, not yet tried for real**

- **Windows:** "Caps Lock: Simplified"; the AutoHotkey script's tray menu choices kept in the registry (its saving and reading code run alone, not the whole script).
- **macOS:** Cmd+Q reaching the remote; `build.sh --install` moving the previous app to the Trash; TigerVNC Viewer as the console window. The Mac parts have only run on macOS 27.
- **IPMIView:** a saved login following a device that's renamed (tested against IPMIView's own classes, not in the running program).
- **Linux:** the viewer's LED sync key kept from the remote (needs a real BMC); the menu entries under WSLg.
- **Container:** Cmd+Shift+V through a live VNC session.
